# 积分套餐与按轮计费（Credit Billing）需求文档

- Feature: `credit-billing`
- 日期: 2026-09-14
- 状态: 已评审（用户确认三项关键决策）

## 背景

当前「念念 Nian」使用「用户自带大模型 Key」的模式：每个用户在设置页填写自己的
API Key，加密存入 `model_configs`；未填写时回退到部署方通过环境变量提供的平台模型
（`PERSONA_PLATFORM_API_KEY`）。这一模式把申请与配置 Key 的门槛留给了用户。

用户明确要求改为平台统一供模并计费：管理员在后台填写大模型 Key，用户不再自行填写；
平台按积分套餐运营；每完成一轮「用户发送 + 模型回复」扣减固定积分；工作台提供用量
圆环展示。

## 关键决策（用户确认）

1. **计费口径**：按轮固定扣分。仅聊天回复计费，一轮消息触发一次成功模型回复扣
   固定积分（默认 1 分/轮）。主动消息、蒸馏、重蒸馏、记忆抽取不单独扣费。
2. **充值与购买**：后台手动发放。管理员在后台为用户发放或扣减积分；前端展示套餐
   档位、余额与用量圆环；本轮不接入真实支付渠道。
3. **套餐与赠送**：内置 3 档套餐；新用户注册赠送 100 积分；移除用户自带 Key 入口，
   统一使用后台配置的平台 Key。

## 术语

- **平台模型（Platform Model）**：由管理员在后台统一配置、供全体用户使用的大模型
  服务，含 API Key、Base URL、模型名与启用状态。
- **积分（Credit）**：平台内计量单位，用户在消耗平台模型能力时按轮扣减。
- **一轮（Turn）**：一次用户消息触发的模型回复过程；同一轮成功调用一次模型计扣一次。
- **每轮单价（Per-turn Cost）**：每成功完成一轮聊天回复所扣减的积分数。
- **套餐（Credit Package）**：后台维护的积分档位，含名称、积分数量、价格、排序与
  启用状态，用于展示与管理员发放参照。
- **额度流水（Credit Ledger）**：积分的每一次增减记录，含操作者、原因、变动值与
  变动后余额。
- **用量圆环（Usage Ring）**：用户界面中以环形进度展示的积分消耗比例，中心展示余额。

## 需求（EARS）

### 平台模型由后台统一管理

- R1: When 管理员在后台提交平台模型的 Base URL、模型名与 API Key, the system
  shall 以加密形式保存该 Key，并使其对后续聊天请求生效。
- R2: While 平台模型处于启用状态, the system shall 使用平台 Key 处理全部聊天回复。
- R3: If 平台模型未配置或未启用, then the system shall 在聊天请求时返回明确的不可用
  提示，并递增一个失败计数指标。
- R4: The system shall 在用户设置页以只读方式展示「由平台提供」，并隐藏用户 API Key
  输入控件。
- R5: When 管理员更新平台模型配置, the system shall 清理已缓存的 Agent 与模型客户端，
  使新配置在下一次请求生效。

### 新用户初始积分

- R6: When 新用户注册成功, the system shall 向该用户积分账户发放初始积分（默认 100），
  并写入一条额度流水。
- R7: Where 管理员调整了初始赠送值, the system shall 按最新配置发放。
- R8: If 初始赠送值配置为 0, then the system shall 跳过发放且不写入流水。

### 按轮扣费

- R9: When 一轮聊天成功获得模型回复, the system shall 从该用户积分账户扣减每轮单价，
  并写入一条额度流水。
- R10: If 用户积分余额小于每轮单价, then the system shall 在调用模型前拒绝该轮，返回
  「积分不足」提示，且不做任何积分变动。
- R11: When 同一轮因去重命中缓存而直接返回, the system shall 不重复扣减积分。
- R12: If 模型调用失败, then the system shall 不扣减积分。
- R13: While 每轮单价配置为 0, the system shall 不扣减积分。
- R14: The system shall 在并发请求下保证积分余额不小于 0。
- R15: When 微信入站消息触发扣费且余额不足, the system shall 向该联系人返回积分不足
  的可读提示，并跳过模型调用。

### 积分套餐与后台发放

- R16: The system shall 内置至少 3 个积分套餐档位，每个档位含名称、积分数量、价格、
  排序与启用状态。
- R17: When 管理员为用户发放或扣减积分, the system shall 更新余额、写入额度流水并写入
  管理员审计记录。
- R18: When 管理员调整套餐档位, the system shall 保存变更并在用户端展示最新档位。
- R19: While 某套餐档位处于停用状态, the system shall 在用户端隐藏该档位。

### 用量圆环与余额展示

- R20: The system shall 在用户工作台展示积分余额与用量圆环。
- R21: When 用户打开工作台或设置页, the system shall 从积分接口读取余额、已用积分、
  累计获得积分与消耗比例。
- R22: While 累计获得积分为 0, the system shall 将消耗比例显示为 0，圆环显示为空进度。
- R23: When 积分发生增减, the system shall 在用户下一次读取时返回最新余额。
- R24: The system shall 在管理员用户列表展示每位用户的当前积分。

### 额度流水可追溯

- R25: The system shall 为每次积分变动记录操作者、原因、变动值与变动后余额。
- R26: When 用户查看积分明细, the system shall 返回该用户最近的若干条流水。
- R27: The system shall 在管理员审计日志中保留积分发放与扣减动作。

## 补充：念念币与兑换码货币模型（2026-09-14 用户确认）

在原有「积分 = 按轮扣减单位」基础上，引入两层货币结构。

### 术语补充

- **念念币（Nian Coin）**：平台唯一钱包货币，用户侧只能通过兑换码获得，用于购买套餐。
- **聊天额度（Chat Quota）**：聊天实际扣减单位，由套餐发放，按轮消耗。
- **兑换码（Redemption Code）**：管理员批量生成的凭证，每个码携带固定念念币数量，
  一次性使用。
- **额度套餐（Quota Package）**：以念念币定价、发放聊天额度的档位。

### 需求（EARS）

- R28: When 管理员生成兑换码, the system shall 按数量与单码念念币生成唯一兑换码，
  并记录批次、备注、创建人与创建时间。
- R29: When 用户提交有效且未使用的兑换码, the system shall 直接向该用户钱包发放对应
  念念币，写入念念币流水，并将该兑换码标记为已使用。
- R30: If 兑换码不存在或已被使用, then the system shall 拒绝兑换并返回明确提示，且不
  变更钱包余额。
- R31: When 用户使用念念币购买某启用套餐, the system shall 在同一事务内扣减对应念念币
  并发放套餐聊天额度，分别写入念念币流水与额度流水。
- R32: If 念念币余额小于套餐定价, then the system shall 拒绝购买、返回「念念币不足」
  提示，且不扣减念念币、不发放额度。
- R33: The system shall 分别维护念念币钱包与聊天额度两套余额与流水，互不混用。
- R34: The system shall 在用户设置页展示念念币余额、聊天额度圆环、兑换码入口与套餐
  兑换按钮。
- R35: The system shall 在管理后台展示念念币概览、兑换码生成与列表、以及以念念币
  定价的套餐编辑器。
- R36: When 管理员调整用户念念币, the system shall 更新钱包余额、写入念念币流水并写入
  管理员审计记录。
- R37: Where 新用户注册赠送, the system shall 将赠送发放为聊天额度（体验额度），
  不作为念念币来源。
